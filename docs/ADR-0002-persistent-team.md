# ADR-0002：可持久化的维护团队（票单台账 + 角色 + 控制台）

- 状态：已采纳（2026-11-10）
- 取代：无
- 相关：[ADR-0001](ADR-0001-architecture.md)、[ROADMAP-v3](ROADMAP-v3.md)

## 1. 问题

单个会话做完整的系统，会撞三堵墙：

1. **上下文会滚雪球**。设计、实现、测试、文档全压在一条对话里，越往后越只能"记住结论"，细节靠猜。
2. **子代理是一次性的**。`subagent` 起一个、干完、结果回到主上下文——没有"这个模块归谁长期维护"的概念；重启后什么都不剩。
3. **中断即失忆**。模型在长任务上会丢线索；只靠对话历史做状态，等于把项目状态放在一个会被压缩的缓冲区里。

## 2. 决策

**把"谁在做什么"从对话里搬到磁盘上。** 维护结构 = 票单台账（append-only）+ 角色契约（文件）+ 控制台（一个界面能看到全部）。

- **台账** `team/tickets.jsonl`：只追加，三种事件 `create / claim / complete / block`；当前状态由重放得出（和 L1 事件流同一套思路）。
  - 好处：重启不丢；冲突可查；"为什么这票卡住"永远有据。
- **角色** `team/roles.json`：每个角色写清"能改哪些目录、完成标准是什么、不许碰什么"。子代理每次启动都只读自己那一份，避免越界改动。
- **控制台**：侧栏新增「控制台」面板，读 `/neuroloop/team`，显示角色、票单、卡住项、下一步。人不看文档也能知道系统在干什么。
- **执行者不持久，台账持久**：worker（子代理 / 定时任务 / 我）是**可替换的**，起一个跑一票、跑完把结论写回台账。这样模型换代、断线、重启，项目都不受影响。

## 3. 票单字段

```jsonc
{
  "id": "T-0007",           // 单调递增，不复用
  "title": "storage：SQLite 投影",
  "role": "core-dev",       // 见 roles.json
  "scope": ["storage/", "test/storage.test.mjs"],
  "deps": [],               // 依赖的票 id；未完成的依赖 → 不可领取
  "accept": ["node --test test/storage.test.mjs 全绿", "check_all.ps1 9/9"],
  "note": ""
}
```

事件：`{t, ev:"create"|"claim"|"complete"|"block", id, by, note}`。

## 4. 生命周期

1. `ready`：所有依赖完成。
2. `claimed`：某个 worker 领取，写 `by`（`lead` / `qa` / 子代理名 / `cron`）。
3. `done` 或 `blocked`：写明结论或阻塞原因；`blocked` 必须写清"等什么"，否则下一个人无法接手。
4. 卡住判定：`claimed` 超过 6 小时没有 `complete`，控制台标黄——不是自动回收，是提醒。

## 5. 与其它层的关系

- 票单**不存代码**，只存"哪一块、谁、到哪一步"。
- 代码真源仍是 git；测试真源是 `tools/check_all.ps1`。
- 与 ADR-0001 一致：一切都是 append-only 事件 + 可重放投影；`team/board.json` 只是缓存，删了能重建。

## 6. 被否方案

| 方案 | 否掉的原因 |
| --- | --- |
| 用对话历史当任务表 | 压缩/重启即丢，且无法并行 |
| 只靠 `subagent` 一把梭 | 一次性，没有归属，无法追责 |
| 上 Temporal/DBOS 这类工作流引擎 | 本机零依赖约束，且项目规模用不上；台账 200 行足够 |
| 每个角色常驻一个会话 | 成本高、易空转；票单驱动更省 |

## 7. 后果

- 好：任何人（包括下一轮的我）先读台账就知道进度；中断成本从"重读对话"降到"读 20 行 JSON"。
- 代价：多一步登记；票单本身会腐烂——所以每周复盘要删过时票、合并碎票。
- 纪律：**没有票单不开工**。修 bug 也先开一票，哪怕只有一行。

## 8. 执行侧（2026-11-11 补）：票怎么真正落到子代理手里

ADR 只说了"要有票"，没说"票怎么被领走"。补这一节，因为**没有执行侧，台账就是备忘录**。

### 8.1 一条命令三个动作

`tools/ticket.mjs` 是唯一的写入点（子代理不手改 `tickets.jsonl`）：

```
node tools/ticket.mjs list                     # 看盘（done 默认不显示）
node tools/ticket.mjs next --role core-dev     # 挑最早一张可领的
node tools/ticket.mjs brief T-0003             # 输出可直接粘贴给子代理的提示词
```

`brief` 不是模板拼接，而是**把票渲染成一段带纪律的作业书**：写域、验收、红线、五步交付流程、
"不要自己标完成"。这样派活的人不需要每次重新解释规矩，规矩写在角色契约里。

### 8.2 为什么 `brief` 要由程序生成

- 人写的提示词会漂移（今天说"随便改"，明天说"别动测试"）；
- 票上已有 `scope / accept / role`，生成即可，避免双份真相；
- 出问题时能复现："当时给它的原文就是 `brief T-0003` 的输出"。

### 8.3 谁来标完成

**Lead**。子代理只 claim，不 complete。原因：`done` 是"验收结论"，不是"我干完了"的自述。
Lead 必须自己再跑一次 `check_all.ps1`，再写 `--note`（note 里放证据行）。

### 8.4 并发

写域重叠不会被文件系统拦住，所以 `new` 时会检查已有未完成票的 `scope`，前缀相交就打警告
（`scopeOverlap` / `conflictsOf`，单测 7 条）。这是**提示**而不是锁：真要并行，先按目录切分。

### 8.5 尚未做的

- 自动派发（定时任务读 `next` 并起子代理）：现在靠 Lead 手动，等演练稳定再做；
- 票的"证据字段"结构化（现在证据写在 note 里，靠人读）；
- 跨仓库的票（同一台机器上多个项目共用一套角色）。
